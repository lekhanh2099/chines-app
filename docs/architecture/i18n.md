# Frontend i18n architecture

This repository uses `next-intl` with locale-prefixed application routes.

## Route contract

Learner/application pages live under `src/app/[locale]/**` and use these locales:

```text
vi
en
zh-CN
```

`vi` is the default locale. Application navigation uses locale-free logical hrefs such as `/settings` or `/reader`; `src/i18n/navigation.ts` owns adding or replacing the locale prefix.

Do not manually concatenate `/vi`, `/en` or `/zh-CN` inside feature components. Use the locale-aware `Link`, `useRouter` and `usePathname` exports from `@/i18n/navigation` for application navigation. Use `localizePathname` only at infrastructure boundaries that must produce an absolute locale-prefixed path, such as auth callbacks or server redirects.

API routes and auth callback endpoints remain unlocalized:

```text
/api/**
/auth/callback
/auth/confirm
```

The proxy composes `next-intl` routing with Supabase session handling. Authentication checks operate on the logical pathname after the locale prefix is removed.

## Message ownership

Messages are split by semantic owner rather than by page file:

```text
messages/<locale>/common.json
messages/<locale>/shell.json
messages/<locale>/auth.json
```

Add one namespace when a feature owns a meaningful body of copy. Register the same namespace for every locale in `src/i18n/messages.ts`.

`Common` is intentionally small. Put a key there only when the concept is genuinely cross-feature, for example `actions.save`, `actions.cancel`, `language` or locale names. Do not move feature-specific sentences into `Common` just because two screens currently happen to use similar wording.

Feature namespaces own domain copy. Examples:

```text
Shell.navigation.items.reader
Shell.profile.logoutSuccess
Auth.validation.invalidEmail
```

Keys describe semantic role, not source-language text. Never use a Vietnamese sentence itself as the key.

## Reuse policy

Before adding a new key:

1. Check the owning feature namespace for an existing key with the same meaning and interaction role.
2. Check `Common` only for genuinely global concepts.
3. Reuse an existing key when the semantic meaning is identical.
4. Add a new key when wording is similar but the product meaning, state or interaction differs.

This prevents one translation from accidentally coupling unrelated features while still avoiding duplicate generic actions.

## Type safety and parity

`src/types/next-intl.d.ts` augments `next-intl` with the repository locale and message contracts. Translation calls should therefore use known keys instead of arbitrary strings.

`src/i18n/messages.test.ts` verifies that `en` and `zh-CN` expose the same semantic leaf keys as the Vietnamese base messages. When adding a key or namespace, update all supported locales in the same change.

## Content versus interface copy

Learning content is not UI translation data. Chinese lesson text, pinyin, Vietnamese explanations, vocab, grammar, exercises and other course content remain owned by HanziHome data sources and their typed view models. Do not copy database/course content into locale message files merely to render it.

Use i18n messages for interface chrome, actions, labels, validation, empty/error states and product instructions whose language follows the selected app locale.

## Adding a new locale

A locale addition must update the single locale owner in `src/i18n/config.ts`, add equivalent message namespaces under `messages/<locale>/`, and verify auth/proxy route behavior. Do not fork navigation configuration or duplicate route trees for a locale.

## Adding a new feature

A new feature should:

- navigate with `@/i18n/navigation`;
- create a feature namespace only when needed;
- reuse `Common` semantic keys rather than duplicating generic actions;
- keep feature content/data separate from UI translations;
- add all locale message variants atomically;
- keep tests capable of detecting missing message keys.
