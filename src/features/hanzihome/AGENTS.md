# HanziHome Subtree Contract

This file applies to `src/features/hanzihome/**` and overrides repository-wide
rules only where it is more specific.

The root policy kernel, local HanziHome contracts and this subtree source
override generic or vendor skill advice. HanziHome skills route the workflow;
they do not redefine these domain invariants.

## 1. Product and content truth

HanziHome is a Chinese self-study workspace.

Current hierarchy:

```text
Course → Book/Volume → Lesson → Module
```

Study Mode and Debug/Audit Mode MUST remain separate. Study Mode is the
learner-facing default; Debug/Audit Mode is explicit and may expose raw or
unmapped data. Lesson content is not edited in the app (no Edit Mode).

Lesson content is checked-in static JSON under `static-json/`:

- textbooks and the converted courses (Giáo trình Hán ngữ, Boya) render in the
  textbook reader. Lesson content is read only on the server
  (`business-chinese-static-content.ts`, `course-textbooks.server.ts`) and
  reaches the browser as route props or through
  `/api/hanzihome/textbooks/[book]/lessons/[number]`;
- Client Components import `static-json/textbook-catalog.ts` (schemas, types and
  lesson lists) and MUST NOT import `business-chinese-static-content.ts`: it
  pulls every textbook into the client bundle. `textbook-catalog.json` is
  generated by `npm run content:textbook-catalog` after a bundled textbook's
  lesson list changes (`npm run content:check` fails when it is stale);
- a lesson that was opened online stays readable offline: the workspace stores
  it in the `hanzihome-textbook-lessons` cache and the service worker serves the
  lesson route from that cache when the network is unavailable;
- the built-in Hanzi Studio courses (`studio-seed.json`) are served by
  `static-json/studio-published-content.server.ts` through the catalog, lesson,
  vocabulary, aggregate and listening routes; unknown ids answer not found;
- radicals (`hanzihome_radicals`) and the vocabulary store rows
  (`hanzihome_vocab_items`) are the remaining database content.

The app MUST NOT mutate static content files, create local JSON write APIs or
silently convert shared content into user-owned rows.

Vocabulary store rows:

- `hanzihome_vocab_items` owns each course vocabulary word or phrase; a row's
  lesson is the converted course lesson listed in
  `static-json/courses/legacy-routes.json`;
- one active word or phrase is unique within a lesson by
  `(lesson_id, word, pinyin)`; the same word MAY appear in another lesson.

Canonical word identity:

- `hanzihome_words` owns one row per written form and reading; a trigger links
  every `hanzihome_vocab_items` row through `word_id`, so writers never submit
  a canonical id;
- the reading key (`hanzihome_word_pinyin_key` in SQL, `wordPinyinKey` in
  TypeScript) ignores tone marks for multi-character words, keeps them for a
  single character, and keys a list of readings by its first one. The two
  implementations MUST stay identical: change them together and regenerate the
  fixtures in `word-key.test.ts` from the SQL function;
- the meaning of a word belongs to its lesson row and is shown per lesson; a
  canonical word carries no meaning.

Explained characters come from the notes in `docs/radicals/`. The JSON under
`static-json/radical-character*.json` is generated by
`npm run content:radical-characters`; `npm run content:check` (part of
`npm run check`) fails when the notes changed without regenerating it.

Import, seed or migration work MUST NOT maintain two independent vocabulary
copies or weaken the active lesson/word/pinyin uniqueness invariant.

Learning records have separate product meanings and MUST NOT be mirrored or
silently synchronized:

- `user_learning_state.progress` owns course mastery for lesson-scoped vocab
  and grammar nodes;
- `hanzihome_words` owns the canonical identity of a written form and reading;
  each `hanzihome_vocab_items` row keeps the meaning of its own lesson;
- `hanzihome_learning_loop_items` owns the due practice queue and scheduling
  state; it is not a second mastery record;
- `hanzihome_practice_attempts` is immutable attempt evidence, not current
  progress state.

Lesson text display preference is owned by `user_learning_state.settings`.
Reader progress owns only completion and exercise answers. Feature stores MUST
NOT mirror either persisted owner. One app-level learning-state sync agent owns
online/focus retry orchestration; consumer hooks only read state and enqueue
mutations.

Learning-state persisted writes require an expected remote version and
deterministic conflict-rebase proof that unrelated remote changes survive.
Consumer hooks MUST NOT install duplicate retry listeners.

Import or bulk-edit work MUST validate the complete input, reconcile counts and
stable identities, and produce a preview/diff before persistence. A mismatch
MUST remain untouched and be reported; preview is not authorization to write.

## 2. Data-loading contract

Before implementing a HanziHome screen, state:

- data required above the fold;
- data loaded only after interaction;
- data that MUST NOT load on the screen;
- owning query/repository/route;
- query key;
- fallback behavior;
- expected payload scope.

Rules:

- Library/dashboard surfaces load summaries, not full lesson details.
- A lesson workspace loads only selected lesson detail.
- The unified vocabulary store (`vocabulary-index/`) owns cross-lesson
  vocabulary: course rows merged with bundled textbooks, speaking drills and
  radical notes. Study surfaces read it through
  `/api/hanzihome/vocabulary/*`; do not build a second cross-lesson index.
- The store index is cached per owner by content revision
  (`getAggregateVocabRevision`); a new read path that changes what the store
  contains must be reflected in that revision.
- Do not fetch all records merely to calculate counts.
- Query keys MUST include every variable that changes returned data.
- Invalidate the smallest correct scope after mutation.

## 3. Editing

Lesson content is changed in the static JSON (and its generators), never from
the app. The only in-app content edits are radicals
(`radical-editing/`, `/api/hanzihome/content/radicals/[entityId]`) and library
collection covers; both are editor-only and use optimistic concurrency.
Non-trivial edit forms use the repository TanStack Form adapter and Zod; the
form library owns form state.

## 4. API and persistence

Server routes MUST:

- derive user identity from the server session;
- verify ownership/editability;
- verify parent-child relationships;
- treat client IDs as expected constraints, not proof;
- avoid destructive multi-step updates without a transaction.

Normal field/node edits SHOULD map to a single-row update whenever practical.

Exercise and practice persistence is high risk. Before supporting a new exercise
family, identify every rendered and persisted subpart.

The family-specific inventory covers metadata, instruction, questions/items,
choices, word bank, answer/key, acceptable answers, explanations, refs,
dialogue, sample answers, cloze segments/answers and matching sides/matches.
Do not generalize one exercise shape to all families.

## 5. Study renderer

Study Mode SHOULD render typed view models.

Flexible or unknown-shape handling belongs in:

- import adapters;
- normalizers;
- audit/debug renderers.

Study Mode MUST NOT silently hide available fields.

If data cannot be rendered safely:

- show a clear fallback;
- report the unmapped shape;
- do not guess arbitrary keys throughout UI components.

## 6. HanziHome UI

Preserve:

- pinyin visibility controls;
- Vietnamese meaning visibility controls;
- answer reveal defaults;
- `lang="zh-CN"` for Chinese text where appropriate;
- iPad portrait usability;
- current study-flow scroll ownership;
- Pinyin selection: ruby Pinyin carries `data-pinyin-selectable`, and code that
  derives a Hanzi selection from a DOM range MUST ignore the selection while
  `isPinyinSelectionActive()` is true;
- source-aligned semantic brand/surface roles defined by the shared UI system; compatibility gradient/glass class names must not render decorative gradients.

Do not expose answer content by default in practice UI.

Do not expose developer JSON in Study Mode.

## 7. Stop conditions

STOP AND CONFIRM before code mutation when:

- DB schema/RLS changes are required;
- a dashboard would need full content loading;
- an exercise shape is unknown;
- a Study renderer would need broad arbitrary JSON guessing;
- the change would break the current Study Mode;
- the task expands from one content family to another without a reviewed
  contract.

## 8. Verification

In addition to repository checks:

- renderer changes: inspect representative real payloads;
- query changes: verify first load, stale/refetch, empty and error states;
- exercise changes: verify every supported subpart;
- UI changes: verify iPad portrait and keyboard interaction.
